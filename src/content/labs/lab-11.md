## 1. Мета роботи

Навчитися інтегрувати REST API у фронтенд-застосунок і типізувати цю
інтеграцію в TypeScript: описувати відповіді API типами за документацією,
писати типізовані запити з `fetch` і `async`/`await`, перетворювати дані з
мережі з `unknown` на перевірені типи й показувати користувачеві стани
завантаження, порожнього результату та помилки. Навчитися перевіряти код,
написаний AI-агентом, компілятором, тестами й панеллю Network.

**Очікуваний результат:** застосунок ShowFinder на TypeScript працює зі
справжнім TVmaze API; `npm run check` показує «Типи: без помилок» і всі тести
пройдено; типи, запити й стани ви написали власноруч, а чернетку AI-агента
перевірили й виправили.

## 2. Цілі та результати навчання

Після виконання лабораторної роботи студент повинен:

- Надсилати запити через `fetch`, читати `ok`, `status`, заголовки й тіло
  відповіді; пояснювати, чому `fetch` не відхиляє проміс на 404 і 500 і коли
  відхиляє.
- Писати асинхронний код з `async`/`await` і `try/catch` так, щоб жодна
  помилка не ставала `Uncaught (in promise)`.
- Пояснювати статуси 200, 404, 429 і 5xx, заголовки `Content-Type`,
  `Cache-Control` і `Access-Control-Allow-Origin` та що саме блокує CORS.
- Досліджувати запити в панелі Network: статус, заголовки, Payload, Preview,
  throttling.
- Описувати відповіді API інтерфейсами TypeScript за документацією й
  справжніми відповідями, з `null` там, де він буває.
- Типізувати функції й класи; розрізняти `unknown` і `any`; звужувати типи
  (`typeof`, `instanceof`, `in`, перевірка поля-дискримінанта) і писати type
  guards.
- Моделювати стани інтерфейсу discriminated union і обробляти їх вичерпно, з
  `never`.
- Пояснювати, що робить `tsc`, що вмикає `strict` і чому типи зникають після
  компіляції.
- Перевіряти код, написаний AI-агентом, компілятором, тестами й у браузері.

### 4.1. HTTP і Fetch API — у браузері

Розпакуйте starter-проєкт (§5.1) і відкрийте `index.html` через Live Preview у
Chrome або Edge за адресою `http://127.0.0.1:…`, а не у вбудованій вкладці
VS Code. Фрагменти вставляйте в Console цієї сторінки: Console дозволяє
`await` без `async`-функції. У Network виберіть фільтр **Fetch/XHR**.

**Е1. Відповідь API.**

```js
const response = await fetch('https://api.tvmaze.com/search/shows?q=girls');
console.log(response.status, response.ok, response.headers.get('content-type'));
const data = await response.json();
console.log(Array.isArray(data), data.length, Object.keys(data[0]));
```

**Проаналізуйте:** що виведе кожен `console.log`? Де в елементі відповіді
назва серіалу? Знайдіть у Network → Response Headers заголовки `cache-control`
і `access-control-allow-origin`: що кожен означає? Відкрийте ту саму адресу з
`?q=kitchen` у новій вкладці: у якого серіалу немає постера чи дати прем'єри і
як це виглядає в JSON?

**Е2. Коли fetch відхиляє проміс.** Домен `.invalid` гарантовано не існує.

```js
const missing = await fetch('https://api.tvmaze.com/shows/999999999');
console.log(missing.ok, missing.status);
console.log(await missing.json());
try {
  await fetch('https://api.tvmaze.invalid/shows/1');
} catch (error) {
  console.log('catch:', error.name, error.message);
}
```

**Проаналізуйте:** чи відхилить `fetch` проміс на 404? Що виведуть перші два
`console.log`? Що потрапить у `catch` і чому саме туди? Що з цього має
робити `getJson` (ТЗ, T2.2)?

**Е3. CORS.** `api.tvmaze.com` — API, `www.tvmaze.com` — сайт для людей.

```js
const api = await fetch('https://api.tvmaze.com/shows/82');
console.log('api:', api.status);
try {
  const site = await fetch('https://www.tvmaze.com/shows/82');
  console.log('www:', site.status);
} catch (error) {
  console.log('www:', error.name, error.message);
}
```

**Проаналізуйте:** що виведе кожен рядок? Чи дійшов запит до
`www.tvmaze.com` і чи прийшла відповідь — що каже Network? Чому ця сама адреса
відкривається у вкладці, а `fetch` зі сторінки — ні? Хто тут дозволяє доступ і
хто його забороняє?

### 4.2. TypeScript — у проєкті

**Е4. `unknown`, `any` і звуження** (після T2). Наведіть курсор у редакторі на
`response.json()` у `getJson`, потім у `searchShows` на дані, які повернула
`getJson`: одразу після `await` і там, де ви їх уже перевірили guard-ом.
Тимчасово допишіть одразу після `await` рядок `console.log(data.length);`
(з вашою назвою змінної), подивіться на помилку й видаліть рядок.

**Проаналізуйте:** який тип має кожен із трьох виразів? Чому `getJson`
оголошено як `Promise<unknown>`, а не `Promise<any>`? Що змінилося б у
`searchShows`, якби вона повертала `any`?

**Е5. Режим strict** (після T1). Створіть тимчасовий файл `src/strict.ts`:

```ts
import type { Show } from './types.ts';

export function posterUrl(show: Show) {
  return show.image.medium;
}

export function shout(text) {
  return text.toUpperCase();
}
```

Запустіть `npm run typecheck`. Потім у `tsconfig.json` тимчасово замініть
`"strict": true` на `"strict": false` і запустіть ще раз.

**Проаналізуйте:** які помилки в `src/strict.ts` покаже компілятор у кожному
випадку? Що зробив би `posterUrl` для серіалу Harlem's Kitchen (id 45962) під
час виконання? Без `strict` з'являється нова помилка в `check/types.check.ts`:
яке правило T1 без `strict` перевірити неможливо і чому? Поверніть
`"strict": true` і видаліть `src/strict.ts`.

**Е6. Що лишається після компіляції** (після T2). Поки працює
`npm run watch`, відкрийте `dist/types.js` і `dist/api.js`.

**Проаналізуйте:** що лишилося від `interface Show`, від `value is Show` і від
`readonly status: number`? Чому `isShow` не можна написати як
`value instanceof Show`? Навіщо перевіряти форму відповіді під час виконання
(ТЗ, T2.7), якщо типи вже є?

## 5. Практична частина: як працювати

Starter-проєкт **ShowFinder** — пошук серіалів у [TVmaze](https://www.tvmaze.com)
на TypeScript. Розмітка, стилі, показ даних і пошук елементів сторінки вже
готові. Порожні чотири файли: `src/types.ts`, `src/api.ts`, `src/state.ts` і
`src/app.ts`.

**Усі завдання практичної частини — у [ТЗ](/labs/lab-11/task/), §4:** T1–T4,
кожне з пронумерованими правилами, а в T4 — ще й запит для AI-агента.
Тримайте ТЗ відкритим під час роботи. Цей розділ — про те, як працювати:
підготовка, правила роботи з AI-агентом і коміти.

**Як перевіряти.** `npm run check` спершу перевіряє типи (`tsc`), потім
запускає тести (`node --test`) і закінчує підсумком «Типи: … · Тести: пройдено
N з M». Назва кожного тесту й коментар біля кожної перевірки типів у
`check/types.check.ts` починаються з номера правила ТЗ. Тести не ходять у
мережу: вони підміняють `fetch` і відповідають записаними відповідями TVmaze,
тож не залежать ні від Wi-Fi, ні від ліміту запитів. Справжній TVmaze і
браузер перевіряє чек-лист Network (ТЗ, §6).

1. Перевірте `node -v`: потрібен Node.js 22.18 або новіший. На старішому тести

3. Виконайте `npm install`, потім `npm run watch` — і лишіть його працювати в
   окремому терміналі.
4. Відкрийте `index.html` через Live Preview у Chrome або Edge: форма пошуку,

5. Запустіть `npm run check`: на початку — багато помилок типів і
   «Тести: пройдено 2 з 40». Прочитайте `README.md` starter-проєкту.
6. Змінюються лише `src/types.ts`, `src/api.ts`, `src/state.ts` і
   `src/app.ts`. Решта файлів — у тому числі `check/` — не змінюється в
   жодному коміті.

### 5.2. Правила роботи з AI-агентом

- **Дослідження (§4).** «Мій прогноз» пишете самі, без AI-агента й до
  запуску.
- **T1–T3 — власноруч.** AI-агент може пояснити документацію TVmaze, помилку
  компілятора, тест чи поняття TypeScript, але не пише код у `src/`. Приклад
  запиту в режимі без редагування (ask / plan):

  > Поясни цю помилку компілятора TypeScript. Нижче — повідомлення, рядок з
  > check/types.check.ts разом із коментарем-правилом і мій тип. Не пиши
  > виправлений код: назви, що в моєму типі не так, і де про це прочитати в
  > TypeScript Handbook.

- **T4 — чотири кроки.**
  1. **Чернетка AI.** Перемкніть AI-агента в IDE в режим, у якому він сам
     змінює файли проєкту (зазвичай — Agent). Закрийте в редакторі вкладки з
     файлами `check/`: багато агентів додають відкриті файли до контексту.
     Вставте в чат **лише** запит T4 з ТЗ, слово в слово, без власних
     уточнень.
  2. **Коміт чернетки.** Нічого не виправляючи, закомітьте все, що змінив
     агент: `T4: AI draft`. Комітьте, навіть якщо чернетка не працює. Якщо
     агент змінив інші файли, крім `src/app.ts`, перед комітом поверніть їх
     командою `git restore -- . ':!src/app.ts'` і запишіть це в підсумок
     звіту.
  3. **Перевірка.** Запустіть `npm run check`. Для кожного тесту чи помилки
     типів, що не пройшли, з'ясуйте, яке правило T4 порушено і чому. Правило
     T4.5 перевірте в браузері. Перегляньте diff чернетки на обмеження ТЗ, §5:
     `any`, `@ts-ignore`, а також `as` і `!` — чи справді вони потрібні.
  4. **Виправлення власноруч.** AI може пояснити тест чи помилку, але **не
     пише** код виправлення. Коли `npm run check` не показує жодної помилки, а
     чек-лист Network проходить, закомітьте виправлення одним комітом:
     `T4: fixes`.

  Якщо чернетка з першого разу пройшла всі перевірки, коміту виправлень немає,
  а в підсумку звіту вкажіть, як ви її перевірили.

У звіті вкажіть назву та версію агента, модель і дату роботи.

## 7. Усний захист

Формат здачі передбачає усну співбесіду за результатами практичної
реалізації. Питання нижче — типові питання співбесіди frontend-розробника з
тем цієї роботи. Відповідайте на прикладах власного коду ShowFinder,
експериментів §4 і панелі Network. Викладач може попросити показати відповідь
у коді чи DevTools або змінити код наживо, без AI. Як оцінюється захист —
§8.

**Питання для підготовки:**

_Fetch API і Promise_

- Що повертає `fetch()`? Коли його проміс відхиляється, а коли виконується
  навіть із помилкою сервера?
- Чим `response.ok` відрізняється від `response.status`?
- Чому `response.json()` теж повертає проміс? Що буде, якщо сервер відповів
  HTML?
- Що повертає async-функція і що стається з винятком, кинутим усередині неї?
- Що означає `Uncaught (in promise)` і як ваш код цього уникає?
- Чим `async`/`await` відрізняється від ланцюжка `then`/`catch`?

_HTTP і REST_

- Що таке REST API? Що означає ідемпотентність методу GET?
- Що означають статуси 200, 404, 429, 500 і 503? Що з цього бачить
  користувач ShowFinder?
- Для чого заголовки `Content-Type` і `Cache-Control`?
- Чому параметри запиту треба кодувати? Що сталося б із «law & order» без
  кодування?

_CORS_

- Що таке Same-Origin Policy і з чого складається origin?
- Хто забезпечує CORS — браузер чи сервер? Що означає
  `Access-Control-Allow-Origin: *`?
- Чому адреса відкривається у вкладці, а `fetch` до неї з іншої сторінки — ні?

_Стани інтерфейсу_

- Які стани має сторінка, що завантажує дані? Чим порожній результат
  відрізняється від помилки — для коду й для користувача?
- Навіщо рядку статусу `role="status"`?
- Що станеться, якщо користувач запустить другий пошук, поки перший ще
  триває? Як цьому запобігти?

_Типи TypeScript_

- Чим `interface` відрізняється від `type`?
- Що таке структурна типізація? Чому об'єкт з API із зайвими полями підходить
  під `Show`?
- Що таке висновування типів (type inference)? Коли тип варто писати явно?
