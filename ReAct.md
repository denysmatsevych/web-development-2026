# Архітектурне рішення: Автоматизована перевірка студентських робіт

## 1. Ціль (Глобальна інженерна задача)
Створити надійну, масштабовну бекенд-систему на TypeScript (Node.js) для автоматичного збору та перевірки розгорнених студентських вебсайтів і супровідних звітів. 

**Навіщо потрібен бекенд:** Обхід обмежень безпеки (CORS та Iframe), виконання важких перевірок у фонових воркерах без навантаження на браузер та централізоване збереження даних без складної авторизації.

---

## 2. План (Архітектурна декомпозиція)
Проєктування структури майбутньої системи перед написанням коду:
* **Архітектурний розподіл (Engine vs. Configs):** 
  * **Engine (Універсальний рушій):** «Сліпий» виконувач, який не знає специфіки конкретної роботи, але вміє виконувати загальні дії: запускати Playwright, міряти розміри вікна, робити скрол, запускати axe-core, перевіряти посилання та передавати URL в браузер.
  * **Configs (Декларативні файли конфігурацій):** Знаходяться у спеціальній папці на бекенді (наприклад, `/configs/labs/`). Оскільки контрольна робота технічно оформлюється за таким самим принципом, вона зберігається як звичайний файл конфігурації (наприклад, `lab-8.config.ts`), а різниця між завданнями визначається через спеціальне поле типу всередині самого файлу (наприклад, `type: 'control'`). Також у конфізі чітко визначається формат звіту, який дозволено здавати для цього завдання (`allowedReportType`: `pdf`, `text` або `any`).
* **Гнучка система оцінювання у конфігах:** Щоб не хардкодити однакові бали для різних завдань, кожен конфіг-файл містить власну шкалу ваги перевірок (`weight`) та загальний максимальний бал, оскільки складність і кількість критеріїв (включно з перевіркою звіту) для кожного завдання унікальні.
* **Ідентифікація без паролів:** Використання списку дозволених пошт (Allowlist) для кожного навчального потоку.
* **Захист адмін-панелі:** Доступ до сторінок викладача та чутливих API-ендпоінтів захищається серверним захистом маршрутів (Middleware) за допомогою секретного токена чи захищеної куки, що повністю блокує доступ звичайним користувачам до адмінки.
* **Схема даних та вибір сховища (Опціональність бази даних):** 
  * Для мінімального робочого прототипу (MVP) база даних не є обов'язковою — історію здач та allowlist можна зберігати у локальних **JSON-файлах** на сервері.
  * Для повноцінної системи з історією перездач та зручною фільтрацією використовується TypeScript ORM (Drizzle або Prisma) із вибором БД:
    * **PostgreSQL:** Рекомендований стандарт для продакшну.
    * **SQLite:** Легкий файл-варіант для простого розгортання.
* **Інтерфейс та сабміт:** Форма для студента містить пошту, посилання на розгорнутий сайт, посилання на репозиторій та **звіт** (формат якого динамічно підлаштовується під вимоги конфігу відповідної лаби чи контрольної — файл PDF або текст), а також захищений дашборд для викладача.
* **Стратегія хостингу (Розгортання системи):** Оскільки стандартний статичний хостинг (GitHub Pages) не підтримує виконання серверного коду та важких браузерних воркерів:
  * **Фронтенд** (сайт курсу, кабінет студента та викладача) залишається на статичному хостингу (GitHub Pages).
  * **Бекенд** (Node.js API, рушій на Playwright та обране сховище даних) розгортається на спеціалізованих платформених сервісах із підтримкою Node.js та фонових процесів (наприклад, **Render** або **Railway**).

## 3. Дія (Реалізація та кодинг)
Написання коду та розгортання компонентів системи згідно з планом:
* **Розробка Бекенд-API:** Створення endpoints для прийому сабмітів (включно з обробкою PDF-файлів або текстових звітів), перевірки пошти по Allowlist та захищених маршрутів для викладача.
* **Реалізація динамічного Engine та валідація звіту:** Написання універсального воркера на Playwright, який під час надсилання роботи зчитує обраний ідентифікатор завдання та динамічно імпортує відповідний конфіг-файл (наприклад, `lab-7.config.ts`). `Engine` перевіряє дотримання дозволеного формату звіту (`allowedReportType`), витягує текст із PDF (через `pdf-parse`) або зчитує вхідний текст, перевіряє його за правилами з конфігу (довжина, ключові слова) та валідує код і верстку сайту. Після цього запускається браузер, емулюються брейкпоінти (320, 375, 768, 1440 px) і сканується доступність через Axe-core.
* **Створення інтерфейсів:** Написання UI для студентської форми здачі робіт (із динамічною зміною інпуту для звіту залежно від конфігу) та захищеної адмін-панелі викладача з можливістю перегляду звітів і ручного коригування (Override).
* **Налаштування деплою:** Конфігурація зв'язку між фронтендом і сервером на Render/Railway, вибір та підключення сховища даних (JSON-файли для MVP або PostgreSQL/SQLite через ORM).

## 4. Оцінка (Верифікація результатів)
Перевірка працездатності та ефективності реалізованого рішення:
* **Тестування рушія та звітів:** Перевірка того, чи коректно Engine динамічно підлаштовується під різні конфіг-файли, чи валідує формати звітів (PDF/текст) і чи правильно підраховує бали відповідно до індивідуальної ваги критеріїв.
* **Зворотний зв'язок для студента:** Оцінка швидкості генерації звіту та зручності повторної здачі (Resubmission) у разі виявлення проблем із сайтом чи звітом.
* **Контроль викладача:** Перевірка того, чи дає дашборд повну картину по потоку, чи надійно захищені адмін-маршрути від сторонніх і чи дозволяє інтерфейс легко керувати оцінками й статусами.
* **Перевірка стабільності сервера та сховища:** Моніторинг того, як сервер справляється із запуском Playwright у хмарі, чи коректно зберігаються дані у вибраному сховищі (JSON або БД) і чи немає таймаутів при скануванні сайтів.
